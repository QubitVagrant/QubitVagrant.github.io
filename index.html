Professional Self-Assessment

As I complete my Bachelor of Science in Computer Science at Southern New Hampshire University, I have developed a broader understanding of what it takes to build reliable software. When I began the program, I was mainly focused on learning individual programming concepts and getting code to work. Throughout my coursework, I learned to look at an application as a complete system that includes the user interface, back-end logic, APIs, databases, security, testing, and the people who will ultimately use it. This growth has strengthened my interest in pursuing a career in software development or full-stack development, where I can work across different parts of an application and continue building practical solutions. I have also learned that successful software development involves more than producing working code. It requires considering maintainability, security, usability, efficiency, and the trade-offs involved in technical decisions.

Growth Through the Computer Science Program

Throughout the Computer Science program, I became more comfortable working with different programming languages, development tools, and areas of software development. Earlier in the program, I often approached assignments by focusing on the immediate problem in front of me. As I progressed through more advanced courses, I started thinking more about how different parts of a system affect one another and how later changes to an application can affect the rest of the system. I gained experience with object-oriented programming, web and mobile development, databases, testing, security, and data structures and algorithms. These areas taught me to break larger problems into smaller pieces, compare different approaches, test my assumptions, and consider performance, validation, maintainability, and security before deciding that a solution is complete.

Several projects throughout the program reinforced this way of thinking. In CS 300, I created a C++ advising program that loaded course information into a binary search tree and used recursive insertion, searching, and in-order traversal to organize and retrieve course data. In CS 340, I worked with Python and MongoDB to create a reusable CRUD module and an interactive dashboard that allowed users to filter and visualize animal shelter data. This experience helped me understand that technical decisions should be based not only on what is easiest to implement, but also on what information the intended user or stakeholder actually needs to make decisions. In CS 360, I developed an Android event-tracking application that used Java and SQLite to manage accounts, events, reminders, and stored user information. These projects used different languages and tools, helping me become more adaptable and choose solutions based on the problem instead of relying on one familiar technology.

Developing the ePortfolio required me to view my work from a different perspective. Instead of viewing each milestone only as a course assignment, I had to evaluate what each enhancement demonstrated about my abilities and how I would present those abilities to a potential employer. Reviewing older projects showed me how much my approach to programming had changed and helped me identify software development and full-stack development as the areas I most want to pursue professionally. Organizing my code review, enhancement narratives, source code, and final project also gave me practice presenting technical work clearly and professionally.

Collaboration and Communication

Another area where I have grown is communication and collaboration. Computer science involves more than writing code. Developers also need to explain their decisions, document their work, respond to feedback, and make changes that other people can understand and maintain. Throughout the program, I became more comfortable describing technical problems and explaining why I chose one approach over another. Projects taught me to consider the needs of the people who will use a system. For example, the CS 340 dashboard required me to translate organizational requirements into filters, a searchable data table, visualizations, and a map that made database information easier for the intended user to understand.

CS 499 strengthened these skills through my code review, written narratives, project documentation, and use of GitHub to track changes and incorporate feedback. The code review required me to explain existing functionality, identify weaknesses, and communicate planned improvements in a way that another developer or manager could follow. I also used source control to separate and document changes as the project developed. Using GitHub and code review showed me how version history, documentation, and clear feedback help other developers understand decisions and contribute effectively to a shared codebase. These experiences helped me see code review, documentation, and source control as more than assignment requirements. They are practices that make technical decisions easier to follow, support collaboration between developers and stakeholders, and reduce the chance that problems are overlooked as a project becomes more complex.

Security and Professional Responsibility

Security became a more important part of how I approached software as I progressed through the Computer Science program. Different projects showed me that an application can function correctly and still have serious weaknesses if authentication, user data, and access are not handled carefully. In CS 360, I developed an Android event-tracking application that stored account and event information in SQLite. Instead of storing passwords directly, I implemented password hashing using PBKDF2 with randomly generated salts and verified passwords against the stored hashes during login. The application also used account-specific database operations and input validation so users could manage only their own information. Implementing these features gave me practical experience thinking about how credentials should be stored, what information should be trusted, and how user data should be separated and protected.

I continued applying these principles in Travlr Getaways by adding role-based authorization, protected administrative operations, ownership checks, server-side validation, inventory controls, and calculations based on trusted database records rather than values supplied by the client. These experiences taught me that security should not be treated as a separate feature that is added after development is finished. It needs to influence decisions involving application architecture, authentication, authorization, database access, validation, and error handling from the beginning. My coursework also made me more aware of privacy and the responsibility developers have when software stores personal information or affects users. I now consider both how a feature is intended to work and how it could be misused when evaluating whether a solution is complete.

Artifact Overview

Travlr Getaways is a full-stack travel management application that I originally created during CS 465: Full Stack Development. It combines a public customer website, an Angular administrator portal, a Node.js and Express REST API, and a MongoDB database. In its original form, visitors could browse travel packages while administrators could add, edit, and delete trip records.

Artifact Selection and Enhancement Goals

I chose Travlr Getaways for my ePortfolio because it gave me a chance to return to a project I had already completed and improve it using skills I developed after CS 465. Since the application includes a public website, an administrator portal, an API, authentication, and database access, it shows my ability to work across several parts of a full-stack system rather than within one isolated component.

My goals were to create a clearer separation between customer and administrator access, strengthen protection around trip-management features, improve validation, and make the application easier to use and maintain. I added customer and administrator roles, included role information in authentication tokens, protected administrator routes and API operations, and added public customer registration, login, account, and logout features. I also created shared validation for the Add and Edit Trip forms, added matching server-side checks, improved error messages, prevented trip codes from being changed after creation, and changed public trip descriptions so stored HTML is displayed as text instead of being rendered by the browser.

Alignment With Computer Science Program Outcomes

This enhancement met the outcome I planned to address involving the use of computing tools, techniques, and software engineering practices to create solutions that provide value. I improved the existing design through reusable authentication middleware, Angular route guards, shared form-validation utilities, clearer API responses, and better separation between public and administrative features. These changes made the application more dependable and easier to maintain without removing its original trip-management functions.

The work also supported the security mindset outcome. The application now checks both the identity and role of a user before allowing trip creation, editing, or deletion. Customer accounts cannot perform administrator actions, and the server validates requests even when someone bypasses the Angular interface. My outcome plan stayed mostly the same, but I narrowed this milestone to authentication, authorization, validation, safe data handling, and maintainability. Recommendation logic and booking features remain part of the later algorithms and database enhancements.

Development Process and Reflection

Enhancing Travlr Getaways helped me better understand the difference between authentication and authorization. A successful login confirms who a user is, but the application still needs to decide what that person is allowed to do. Adding customer and administrator roles showed me why permissions need to be enforced in both the user interface and the API. I also learned why validation is needed at more than one level. Angular validation gives users immediate feedback, while Express validation protects the database from requests that do not come through the form.

Several problems required me to test each part of the application separately. The Edit Trip page remained stuck on a loading message even though the API returned the correct record. I resolved that issue by using Angular signals so the page reacted to the completed request. The navbar also continued to display “Sign In” after an administrator logged in, so I changed the authentication state to update reactively when the token was saved or removed. I tested invalid requests directly against the API to confirm that past dates, invalid trip lengths, and attempts to change a trip code were rejected. Working through these issues improved my ability to trace problems across the frontend, API, and database while making changes without breaking the existing application.

Algorithms and Data Structures

The original Travlr application displayed travel packages but provided no way to determine which trips best matched a customer's preferences. I enhanced the application with a weighted recommendation algorithm that evaluates trip objects using budget, trip or resort name, start date, and trip length.

The algorithm scores, filters, and sorts matching trips and uses deterministic tie-breaking rules to produce consistent results. I also added a recommendation API endpoint, public trip-finder form, match explanations, and automated tests covering scoring, sorting, blank preferences, tied results, and no-match conditions.

Artifact Overview

It combines a public customer website, an Angular administrator portal, a Node.js and Express REST API, and a MongoDB database. Artifact Selection and Enhancement

I selected Travlr Getaways for my ePortfolio because it demonstrates my ability to improve an existing full-stack application with algorithmic problem-solving. The original application displayed available travel packages, but customers had no way to determine which trips best matched their preferences. This limitation made the project a strong choice for an algorithms and data structures enhancement because the existing collection of trip objects could be evaluated, filtered, and sorted to produce more useful results.

The enhanced application includes a weighted recommendation algorithm that compares each trip with a customer's preferred budget, trip or resort name, start date, and trip length. The algorithm awards up to 35 points for budget, 30 points for the trip or resort match, 20 points for the start date, and 15 points for trip length. It processes arrays of structured trip objects, calculates scores, filters unsuitable results, and sorts matching trips from strongest to weakest. Deterministic tie-breaking rules based on price, start date, and trip code ensure that equal scores produce consistent results.

I further improved the artifact by adding a recommendation API endpoint, a public trip-finder form, match explanations, and automated tests for parsing, scoring, sorting, no-match results, tie conditions, and preservation of the original trip order.

Alignment With Computer Science Program Outcomes

This enhancement met the primary course outcome I planned to address by designing and evaluating a computing solution using algorithmic principles and appropriate computer science practices. I transformed the original trip listing into a weighted recommendation system that evaluates structured trip data according to customer preferences.

The enhancement also supported the outcome involving the use of computing tools and techniques to create solutions that provide value. I integrated the recommendation logic into the existing Node.js and Express API, connected it to a public trip-finder interface, and added automated tests for parsing, scoring, sorting, no-match results, and tied results. The match explanations also supported clear communication by helping users understand why each trip was recommended.

Development Process and Reflection

Enhancing Travlr Getaways gave me a better understanding of how algorithms and data structures can improve the usefulness of an application. The trip records are stored as structured objects within an array, and the recommendation process evaluates each object against the customer's preferences. I used scoring, filtering, and sorting operations to organize the trip data and return the strongest matches first.

While building the enhancement, I had to account for blank preferences, partial matches, tied scores, and searches that returned no results. Blank fields were excluded from scoring so they would not unfairly lower a trip's result. When multiple trips received the same score, I used price, start date, and trip code as tie-breakers to keep the order predictable. Testing these situations helped me better understand how edge cases affect an algorithm and why consistent sorting rules matter.

Artifact Overview

Travlr Getaways is a full-stack travel management application that I originally created during CS 465: Full Stack Development. It combines a public customer website, an Angular administrator portal, a Node.js and Express REST API, and a MongoDB database. In its original form, visitors could browse travel packages while administrators could add, edit, and delete trip records.

Artifact Selection and Enhancement

I selected Travlr Getaways for my ePortfolio because it shows how I can improve the database portion of an existing full-stack application. The original project used MongoDB to store trip and user records, but customers could only browse the available travel packages. They could not make reservations, select room or dining options, view their booking history, or cancel a booking.

The enhanced application includes a Booking model that connects each reservation to an authenticated customer and a specific trip. Booking records store traveler information, room and dining selections, prices, booking status, and a unique booking reference. I also expanded the Trip model with room types, occupancy limits, available-room quantities, dining options, resort locations, and image galleries.

The server calculates reservation prices from database records instead of trusting values sent by the browser. I also moved the Travel Blog into MongoDB by adding article records, unique slugs, draft and published statuses, publication dates, public article pages, and administrator management features.

Alignment With Computer Science Program Outcomes

This enhancement met Course Outcome 3 by requiring decisions about how bookings should connect to customers and trips, how room availability should be updated, and what information should be preserved after a reservation is created. I used references to connect booking records to the original user and trip documents while also storing copies of selected trip, room, dining, and pricing information so reservations remain accurate if an administrator later changes the original trip record.

The enhancement also met Course Outcome 4 through the use of MongoDB, Mongoose schemas, Express controllers, REST API routes, database indexes, authentication middleware, and Angular pages. It supported Course Outcome 5 by requiring authentication for bookings, limiting customers to their own reservation records, restricting trip and article management to administrators, validating information on the server, and calculating prices from trusted database records.

Development Process and Reflection

Enhancing Travlr Getaways helped me understand how quickly database work can grow when several features depend on the same data. As I added bookings, room inventory, pricing, dining options, cancellations, and article management, some controller and validation code became long and difficult to manage. One change could affect the database schemas, API routes, public pages, and administrator portal.

Working through these problems showed me the importance of breaking larger tasks into smaller functions, keeping database responsibilities organized, and testing each part before moving to the next feature. This process improved my understanding of database relationships, data consistency, validation, access control, and the need to manage the size and scope of an enhancement as it develops.
